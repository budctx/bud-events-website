## HTTP contract

`POST /api/commerce` accepts JSON with `action`:

| Action | Fields | Server behavior |
| --- | --- | --- |
| `balance` | none | Read slot credits for verified host |
| `start` | `title`, `idempotencyKey` (16–100 ASCII letters/digits/underscore/hyphen) | One transactional start RPC; repeated identical key returns original event |
| `resume` | `eventId` UUID | Owned event read; no debit |
| `checkout` | none | 503 `CHECKOUT_NOT_CONFIGURED`; no fictional payment URL |

All actions require Bearer token, configured HTTPS origin and server verification against Supabase `/auth/v1/user`. Returned Auth identities must include Discord. Host ID comes only from that verified response. Client `hostId`, `userId`, `credits`, `amount`, `paymentId` or `verified` fields are rejected. No auth is required for catalog browsing or local game rehearsal.

Server-only environment requirements: `BUD_BACKEND_ENABLED=true`, exact `SUPABASE_URL` for this development project, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, and `BUD_APP_ORIGIN` (an HTTPS origin without trailing slash/path). Never prefix a service secret with `VITE_`; nothing under `src/` imports the server module. No variables were configured by this increment. Missing config returns 503; unauthenticated callers return 401. Private upstream errors are mapped to fixed codes without leaking raw diagnostics.

`POST /api/whop-webhook` deliberately returns 503 `WHOP_VERIFIER_NOT_CONFIGURED` for every request. There is no unverified HTTP route to credit slots. Whop SDK verification, sandbox account/API key/webhook registration and approved product-price mapping remain required. A success redirect or client claim never grants credits.

## SQL invariants

- `bud_platform`: wallets, server-owned checkout orders, events, manual winners, webhook receipts and append-only credit ledger. No participant signup, attendance, Discord player identities or selection system.
- Every table has RLS. `anon`/`authenticated` have neither schema usage nor callable RPC grants. Narrow public RPC wrappers use **SECURITY INVOKER**, empty `search_path`, qualified names, and execute grants to `service_role` only. Server derives the host before invoking them; public clients cannot choose an arbitrary host.
- Verified-purchase function requires an existing server-owned order and matching sandbox/company/product/currency/minor-unit amount. It locks the order and wallet. Unique payment/message/order fulfillment plus ledger source keys prevent repeated +1. No HTTP code invokes this function until provider verification is implemented and reviewed.
- Start locks the host wallet, returns existing `(host,start_key)` before charging, rejects a reused key with changed title, enforces one active event, checks credit and atomically inserts event, -1 ledger and balance update. Any error rolls back all effects.
- Resume selects by both host and event ID and contains no writes. Manual winner write API is absent until round-adjudication/version contracts are implemented.
- SQL supports only the currently scoped slot/start foundation. It is **not** the full game engine, billing/refund/dispute policy, server card bank, lease/recovery system or final retention contract.
