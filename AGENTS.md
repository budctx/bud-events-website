# BU’D implementation guidance for coding agents

These instructions apply to the current `budctx/bud-events-website` codebase. They supplement, but do not replace, Expert Department OS instructions. Verify dates and current status in Notion and production before changing an integration.

1. **Authority and documentation:** latest explicit owner decision → Notion decision registry and current Stage specs → approved live product/code as implementation and visual evidence → legacy archives for history only. Notion is the canonical progress and acceptance record. Use code-first; do not return to Figma.
2. **Product:** BU’D is a multi-product platform: Home, Events, Bots, Designs. `سؤال وشرط` is the first event. Do not reintroduce participants, bot-required flows, discarded legacy attendee selection, Dark Mode, ghost CTAs or fabricated testimonials.
3. **UX:** Arabic-only product and RTL layout, Light-only visual identity, Readex Pro, approved BU’D assets and colors, mobile/desktop, viewport-safe controls, keyboard/focus accessibility and reduced-motion support. Old AR/EN or LTR requirements are not acceptance criteria for current product; avoid creating new English-facing UI. Retain legacy URL compatibility where needed.
4. **Event runtime:** an authenticated Discord host starts an approved event. The server validates owner/permissions/content and debits **one Slot exactly once** for a new paid start; progress, card reveals, timers, draws, winners and prizes run and save **only in the starting browser**. There is no server restoration of lost local progress. Local game data cannot credit wallets or change payment entitlements. Do not reintroduce server-side game state or upload private winners and prizes.
5. **Commerce and owner operations:** this is an actual production-integrated site, not a sandbox-only demo. Whop checkout, payment jobs, the owner panel and Redeem have production components and sensitive credentials/configuration; never assert payment fulfillment from a READY deployment or a mocked test. The known paid 3 SAR order remains unfulfilled pending authoritative Whop reconciliation. Never issue a compensating admin grant or initiate a new live charge as a test. Protect owner authorization, audit and credit ledgers, idempotency, database RLS, secret scopes and transaction safety. Do not activate/rotate credentials or make real grants/financial changes without owner authorization.
6. **Change workflow:** favor a narrow branch and PR for review, run `npm run typecheck:server`, `npm run build` and `npm test` on the exact SHA and inspect GitHub CI before merging. The owner directs completed approved work to `main`; merges trigger production Vercel deployments. Record exact commit, tests, environment, deployment and caveats in Notion. CI success alone never closes a Stage, gate or owner approval.
7. **Safe cleanup:** verify each branch against `main`, open PRs, deployment links, rollback references and active dependencies before deletion. Keep diverged branches until reconciled, and do not delete financial records, Supabase migrations, Vercel production projects/secrets, Notion approval history or paid order evidence. Historical docs `docs/implementation.md`, `docs/verification.md` and `docs/bot-impact-study.md` are archives, not active requirements.
8. **Repository protection:** as checked on 2026-10-26, `main` reports `protected=false` and the repository ruleset list is empty. Protect `main` with required passing `Website checks / verify` and `owner-database-concurrency`, PR reviews when workable, prevent force pushes and deletion, and confirm the rule actually applies. This needs GitHub repository administration; no workflow file, documentation note or test result substitutes for a live enabled ruleset.
